My opinion

Endorse the proposal — direction, scope, and sequencing are all right. Specifics:

    The core premise is confirmed, not just plausible. Chromium maintains a separate WebSocket socket pool with a limit of 255 per connection group/host, next to the 6-connection HTTP/1.1 pool; Firefox defaults to 200 concurrent WS sessions. So "off the HTTP pool" is exactly what you get, and per-feature sockets are nowhere near any limit.
    ws vs hand-written is not a close call — grant the dependency. Node 24 core ships a WebSocket client only (undici); there is no server. ws has zero required runtime deps, is the de facto standard, and its noServer: true + handleUpgrade pattern maps 1:1 onto the fact that backend.ts owns the createServer instance and routes via regex — no framework in the way. Its security record (last advisory June 2024, promptly patched) is an argument for it: hand-rolling RFC 6455 masking/framing/close handling is precisely the kind of security-sensitive code a maintained library should own. Socket.IO is the wrong tool (own wire protocol, reconnect machinery you'd duplicate); websocket-node is semi-dormant; µWebSockets.js is a different server stack.
    Binary frames: yes, unambiguously. CDP's base64 is an artifact of CDP's JSON transport, not a requirement for ours. Decode once server-side (Buffer.from(data, 'base64')), send JPEG bytes as binary messages. Precedent: noVNC/websockify deliberately dropped base64 WS payloads for binary. This kills the ~33% expansion and the per-frame giant-string JSON.parse on the tab.
    Input over the socket is the second half of the win. Today's stop-gap (documented at src/api.ts:637 as waiting for this very proposal) still pays one request per event and one pool connection while active. In-order WS messages with client-side move coalescing strictly dominate it, and match the terminal's existing createOrderedSender precedent.
    Two refinements I'd push:
        Treat the Origin/Host guard as shared infrastructure, not socket-local. Research confirmed there is no Origin or Host validation on any existing route — a malicious page can already fire state-changing POSTs at the HTTP API (CSRF-style; it can't read responses, but it can drive your browser actions). Write the allowlist as one helper in backend.ts, use it for the upgrade handler now, and apply it to routes as the immediate follow-up — don't let it live only inside the socket path.
        Time-box the SSE fallback. Running two correct transports indefinitely doubles the surface. The prototype phase should end with a decision, and I'd consider deleting the SSE path sooner rather than later once the success criteria hold — the proposal's step 2 says this, but make it a hard gate, not a "when convenient."

Answers to the open questions

1. ws vs hand-written — ws, per above. One addition: set maxPayload explicitly on the server (inbound is only small input JSON; something like 64 KiB is generous — the default is 100 MiB). Attach with noServer: true, validate path/workspace/Origin/Host in your own upgrade handler in backend.ts, then handleUpgrade. That keeps backend.ts the single routing/validation boundary, as the proposal requires.

2. Binary vs base64; <img> vs createImageBitmap — Binary, as above. For the header: start with a fixed 4-byte sequence number (or no header at all until frameAck exists). An 8-byte header with metadata is speculative — you have no metadata today, and adding a prefix later is cheap for a prototype-only wire format. For rendering: start with <img> + blob: object URL (revoke the previous one) and decoding="async". It's the minimal diff from today's data: URL assignment (blob: additionally avoids the data-URL encode/copy), and research found no benchmark-backed winner. Important nuance: Chrome's own guidance says main-thread createImageBitmap() is not guaranteed to decode off the main thread — you'd need a worker + transferable bitmap for that. So only reach for canvas/worker if the prototype's tab-CPU measurements show decode jank; don't pre-build the machinery.

3. Latest-wins vs acknowledgement pacing — Ship latest-wins alone. It's the same idea as today's writableLength > 512 KiB skip (backend.ts:948–950) but per-viewer and applied before buffering rather than after. Keep Chrome-side pacing (minAckIntervalMs = 80, browser-session.ts:47–49) as the global rate limiter, as proposed. Two reasons frameAck is probably never needed: a hidden tab is already handled correctly by closing the socket (in background tabs, WS delivery continues but rAF stops and timers throttle to ~1/s — an open hidden socket would burn bandwidth for nothing; the proposal's close-when-hidden rule is the right answer, keep it non-negotiable), and a visible but slow tab is already covered by the server-side buffered-amount check. Design the seq number in from day one so the option stays open, but don't implement the ack until measurements demand it.

4. Browser WS connection limits — Confirmed: Chrome 255 per host/group (separate pool), Firefox 200 concurrent by default (hard cap 1000). Three tabs × (browser + future terminal) is trivially within budget. Not a constraint at any realistic scale of this tool.

5. Per-feature vs multiplexed per tab — Per-feature, as the proposal suggests. It matches ownership boundaries (the browser feature owns its socket session end-to-end, terminal later), isolates reconnect and flow control per concern, and the connection counts are irrelevant (see #4). On /api/events (rollout step 4): I'd lean keep it on SSE permanently. Verified: /api/events has no Last-Event-ID replay today anyway (only the terminal stream does), and once frames and terminal leave HTTP, the pool pressure drops to one connection per tab — which is acceptable. EventSource's free auto-reconnect is worth keeping for the correctness-critical stream; that's the one place you want the browser's battle-tested reconnect rather than your own.

6. Vite proxy ws: true — One-line change to object form: '/api': { target: ..., ws: true }. It's dev-only (production serves from the backend port). One caveat I couldn't fully verify from public docs: what the proxy does to the Host header on upgrades — http-proxy forwards the original localhost:5173 host unless changeOrigin is set. Your Host-header allowlist must account for both the Vite origin and the backend origin in dev (or set changeOrigin). Decide this in the prototype, since a strict Host check that breaks dev upgrades is the classic first bug of this migration. Backend-restart behavior under the proxy is likewise just "socket dies, client backoff-reconnects when the backend returns" — your reconnect design already covers it.

7. Origin allowlist — Derive it from configuration, don't hardcode: the backend origin (127.0.0.1 and localhost forms of the backend port, both needed since users type either) plus the Vite dev origin (PI_LIVECRAFT_BACKEND_PORT already exists; add the Vite port similarly). On upgrades, reject a missing Origin — browsers always send it, so absent means a non-browser client the viewer doesn't need. Per OWASP: exact-match allowlist, no substrings or wildcards, and remember Origin is not authentication — for a loopback-only tool binding 127.0.0.1, Origin + Host (DNS-rebinding defense) is the proportionate posture.

Smaller notes

    The diagnostics plan is right: a separate browser-socket gauge kind plus frames-sent/dropped counters gives you the before/after evidence the success criteria need.
    One success criterion I'd add explicitly: input ordering (press → release → wheel sequences survive) — it's the regression most likely to silently slip, and it's cheap to assert in a focused test since dispatch is now sequential per viewer.
    The proposal's "Node 22 ships a WebSocket client" line is slightly stale for this repo (engines.node >= 24), but the substantive claim — no core server — holds.

Bottom line: implement roughly as written, with ws approved, binary frames + 4-byte seq, <img>+blob rendering, latest-wins only, per-feature sockets, and the Origin/Host guard built as a reusable helper with route-wide application as the named follow-up.
